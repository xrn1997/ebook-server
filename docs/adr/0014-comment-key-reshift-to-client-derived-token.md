# 评论聚合键换轨为客户端派生的 comment_key

客户端 M2（来源分组与评论）把评论的聚合键从「书源章节 URL」换成了客户端自己派生的不透明
token `comment_key`，跨仓库契约见 android-ebook 的
`docs/superpowers/specs/2026-09-05-m2-comment-api-contract.md`。换轨的理由是旧键在真实场景下
根本不成立：不同用户用不同书源，同一本书的 `chapter_url` 就不同，评论聚不到一起；本地书的
`chapter_url` 是 `md5_章号`，只有本机认得；书籍级评论靠明文 `book_name` 文本列聚合，无索引、
实际已失效。而 [ADR-0013](0013-comment-key-migration-and-admin-api.md) 的 migrate-key 只解决了
「键变了要搬家」，没解决「键本身选错了」——本 ADR 记录换轨本身，并**部分作废** ADR-0013 §1/§2。

换轨前服务端的状态是致命的：`comment_key` 这个字段在请求结构体里根本不存在，Gin 会静默丢弃
未知字段，于是新客户端发出的每一条评论都落进 `chapter_url` 为空串的桶，而新客户端只按
`comment_keys` 查询、永远不命中空串——评论写进去就丢，且全程没有任何错误迹象。

## 决策

### 1. `comments` 新增 `comment_key` 列，成为唯一聚合键；`chapter_url` 降级为兼容读路径

* 新列 `comment_key TEXT` + 索引（按它过滤是公开列表的主路径），AutoMigrate 建列，旧行默认空串。
* **旧行不重算**：`ck1:` 键的输入是「归一化书名 + 归一化作者」，而 `comments` 从未存过作者
  （只有明文书名快照），服务端在信息论上就算不出正确的键。所以 `chapter_url` 列和它的查询参数
  都保留，标注已废弃——这是那些行唯一的可达途径。
* `chapter_name` / `book_name` 保留，语义收窄为**纯展示快照**，不再参与聚合。
* 直接复用旧列改名（`chapter_url` → `comment_key`）**被拒**：旧值是 URL、新值是 `ck1:hash`，
  改名后旧值没有任何客户端会再查询，等于把可读的旧数据变成彻底的死数据，还顺手删掉了兼容路径。

### 2. 创建评论 `comment_key` 必填（`binding:"required,max=200"`）

* 缺键的评论落进空桶后没有任何读路径能捞回来，因此宁可回 `A0400` 让客户端当场发现，
  也不静默接受——这条由 `TestCommentHandler_Create_MissingCommentKey` 守住。
* **这是针对旧客户端的破坏性变更**：只发 `chapter_url` 的 pre-M2 客户端此后无法再发评论
  （读不受影响）。接受该代价，因为「静默丢评论」比「旧客户端发不出评论」严重得多。
* 长度上限 200 是防脏数据与防打满绑定变量，**不是**格式校验：`ck1:` + 64 位十六进制 +
  `#章序号` 实际 69+ 字节，留的是算法版本递增的余量。三处约束（读过滤常量、创建 tag、
  迁移 tag）由 `TestCommentKeyLengthLimitMatchesModelBinding` 用反射钉成同一个数。

### 3. `GET /api/comments?comment_keys=` 逗号分隔多键返回并集，优先于旧参数

* 真实客户端用单个 `@Query` 把多个键拼成逗号串，因此解析按逗号切分，同时容忍
  `?comment_keys=a&comment_keys=b` 的重复参数形态。键本身永不含逗号，切分无歧义。
* 两参数同时出现时 `comment_keys` 胜出、`book_name` 不参与收窄（书名已不是聚合维度）——
  否则结果集是交集还是并集全靠实现顺序。
* 两条入参上限与 `chapter_url` 同源（一条语句的绑定变量总数），因此抽成共用的
  `maxKeyFilters`；`?comment_keys=` 留空按「未提供」处理，落全局最新列表。
* **不做前缀匹配**：客户端总是传完整键（章评键由其枚举构造），支持 `LIKE 'ck1:x%'` 会让
  `#` 后缀失去意义，还得为 text 列前缀扫额外设计索引。

### 4. `migrate-key` 改名 `migrate`，作用列从 `chapter_url` 改指 `comment_key`

* 路径以契约为准（spec §3.2.5 写的是 `/api/comments/migrate`），旧名不保留别名：
  唯一调用方就是新客户端，留别名正是本仓库一贯拒绝的兼容垫片。
* 空串旧键的语义随之改写：过去空 = 「书籍级评论」这个合法桶，现在空 = 「尚未换键的历史行」，
  于是 `old_key=""` 成了用户把自己旧评论一次性收进正确桶的顺手动作。
* **`new_key` 从 `omitempty` 收紧为 `required`**（推翻 ADR-0013 §1 的「两键都用 omitempty」）：
  公开读路径会丢弃空键（`?comment_keys=` 留空按未提供处理），因此迁往空键的评论再也无法按键
  查回，只能靠 `/my` 或全量列表偶然掠过——这与 §2 拒绝「创建时缺键」致命的正是同一件事，
  不能从迁移侧开后门。旧契约里「章节→书籍级」那个方向在 M2 由「迁往不含 `#` 的作品键」表达，
  空 `new_key` 不再有任何正当用途。两键同时为空因此改判 `A0400`（在 required 上就被拒），
  不再走到 `A0305`。

### 5. 全局改键 `rehash` 落在后台引擎：`POST /admin/api/comments/rehash`

跨用户改键是运维能力（某个键算错了，错桶上聚着大量他人评论，只动本人行的 migrate 救不了场）。

## 与上游契约的两处偏离

1. **rehash 不在公开 API。** spec §3.2.6 把它写成 `POST /api/comments/rehash` 且「需要管理员
   权限」——但公开端口上没有管理员鉴权体系（ADR-0010：后台是**独立 Gin 引擎 + 独立监听地址 +
   独立 JWT**，默认只绑 127.0.0.1）。照搬到公开端口等于在公网暴露一个跨用户写接口，
   且没有任何现成的身份能判它「是管理员」。因此实现为 `POST /admin/api/comments/rehash`。
   客户端不调用它，改路径不阻塞对齐。
2. **`comment_key` 空值序列化为 `""` 而非 `null`。** spec §3.3 说旧数据"可能为 null"；Go 侧
   `string` 零值是空串，为区分二者要把视图字段换成 `*string`。客户端对 null 与 `""` 的处理
   完全一致（拆分后 `filter { it.isNotEmpty() }`），因此不引入这层间接。

## 后端无法满足的部分

* **旧行无法自动换轨**（见 §1）：缺作者字段，服务端算不出 `ck1` 键。旧数据的出路只有两条，
  都需要人工提供书名+作者：用户自己的行走 `POST /api/comments/migrate?old_key=""`，
  全站性的错桶走 `POST /admin/api/comments/rehash`。没有第三种自动化方案。
* **服务端不能校验键的正确性**：不校验不是偷懒，是 M2 的设计前提——键由客户端无协调地派生，
  服务端一旦校验就得复制归一化规则，规则版本从此两处各一份、静默漂移。

## 被拒方案

* **`comment_key` 用 `omitempty`**：即本次要修的那个 bug 本身——静默收下缺键请求，评论永久丢失。
* **保留 `migrate-key` 作为 `migrate` 的别名**：兼容垫片，且会让「迁移的是哪一列」在两处路由间含糊。
* **`comment_keys` 支持前缀匹配**：见 §3。
* **在公开端口实现 rehash**：见「与上游契约的两处偏离」§1。
* **后端建书籍表 / 提供「列出所有书」**：违反 spec 不变量 2，且会把「不存书籍数据」这条边界毁掉。

## 下游影响

* `AutoMigrate` 为 `comments` 加一列带索引的 TEXT，旧行取默认空串——无数据迁移脚本，无停机。
* pre-M2 客户端：读评论、按 `chapter_url` 过滤均不受影响；**发评论会被 `A0400` 拒**（§2）。
* 桌面管理应用（`desktop/`）不受影响：它的评论视图不使用 `chapter_url`，也未调用迁移端点。
* 客户端 `book_group` 表是键的唯一权威（哪个 noteUrl 属于哪个键、主键是哪行都在客户端），
  服务端只提供按键过滤与按键搬家，不参与归属判断。

## 验收

* `go test ./...` 覆盖：缺键创建被拒 A0400、`comment_key` 原样回显、逗号多键并集、单键精确匹配
  （`#` 后缀不做前缀匹配）、`comment_keys` 不命中未换键旧行、两参数同时出现时新键优先、
  空 `comment_keys` 被忽略、两条入参上限、`chapter_url` 兼容读路径仍读出旧行、
  迁移作用于 `comment_key`（含空旧键收拢本人旧行、迁往空键退回、幂等重试返回 0、用户隔离）、
  后台 rehash 跨用户生效 / 同键 A0305 / 空 old_key A0400 / 未带后台 token A0403、
  三处长度约束反射钉死一致。
* 响应视图新增 `comment_key`，其余字段（user 四字段、`add_time` 上海时区）不变。
