# 发码编排收拢进验证码发送纵深模块

Status: accepted

「下发验证码」与「校验验证码」都收拢进 `service` 包内的 `VerificationCodes` 纵深模块：限流器与流程键符号表随模块归位，存储键的拼法只有模块自己知道，调用方只递流程、邮箱（与码）并接一条领域错误。模块对账号无感（枚举隐藏仍留在找回流程，ADR-0006）。

## 背景

「给某邮箱在某流程下发一个验证码」曾被复制在三处，注册、找回密码与账号注销各有一份编排：各自挂着**一对限流器**（每分钟 1 次、每小时 5 次）、各自调限流判断 + 存码 + 派发邮件。限流器状态**散落在每个 service 实例上**，而不是「下发验证码」这一域概念的一个属性。流程前缀裸字符串（`"reg:"`/`"forgot:"`/`"del:"`）同时充当存储命名空间与限流配额键，这份隐式耦合没有归属：改编码键而不改限流键，两个流程的配额会被意外合并。

校验半边曾留在调用方：注册、找回与注销三处各自重拼存储键、各自解释 `pkg/code` 的四值结果枚举。枚举外泄当场就付出了代价——注册流程把「尝试超限」与「码不符」「无码」一起折成「验证码错误」，于是 `A0241` 在 `/api/auth/register` 上永不可达。

## 决策

1. **模块住在 `backend/service/verification.go`**：`VerificationCodes` 对外只露两个动词——`Send(ctx, flow, email) error` 与 `Confirm(ctx, flow, email, code) error`。`main.go` 建唯一实例注入认证与账号模块。

2. **全权归属限流 + 键符号表 + 存码 + 发信**：模块内拥有一对限流器（按 flow+email 隔离配额：每分钟 1 次、每小时 5 次）、流程前缀符号表、存码与派发邮件。对「注册→找回→注销」的限流语义一处可改。

3. **`Flow` 类型化枚举**（`FlowRegister`/`FlowForgot`/`FlowDeletion`）：前缀映射（`":"` 串）是模块的私有符号表，对外不暴露；存储命名空间与限流配额同源，新增流程只加一枚举值 + 一处前缀映射。

4. **存储键的拼法只有模块知道**：TTL、尝试上限与四值结果枚举仍由 `pkg/code` 导出，但生产代码里只有 `Confirm` 一处解释它们；调用方拿到的只是领域错误。`pkg/code.Store` 不再提供 `Set`——测试经 `Send` 加记录型 Mailer 取码，不再猜命名空间。

5. **模块对账号无感**：不持有 `UserStore`。找回密码的「账号不存在也成功」是**防枚举策略**（ADR-0006），留在 `SendForgotCode` 调用点，不进模块。

6. **对外契约不变**：任何 API 请求/响应与收拢前完全一致；`/api/auth/register` 多了一种此前就该能回出的错误码。

## 被拒方案

* **只打包存储与邮件、限流留在调用方**：只是把复杂度移走而非收拢，浅一半，删除测试不过。

* **模块感知账号（`SendOnlyIfExists` 变体）**：让「发码」依赖「账号」，多一条依赖轴，稀释纵深；枚举隐藏是流程策略而非发码职责。

* **模块入住 `pkg/verification` / `pkg/code`**：把业务流程编排当基础库对待，需为 `Flow` 枚举与限流参数在包间立契约，撑大接口；它与 ADR-0007「service 内聚编排」相悖。

## 边界

- 依赖以具体类型注入（ADR-0007）：`code.Store` 与 `Mailer` 由 `main.go` 装配唯一实例，第二适配器出现前不立 seam。
- 验证码的 TTL 与尝试上限归 `pkg/code`，模块不另设一份。

锚点：`backend/service/verification.go` 的 `VerificationCodes`；`backend/pkg/code`；`backend/service/auth.go` 的 `Register`。
