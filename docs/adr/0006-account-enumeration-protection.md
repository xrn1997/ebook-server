# 统一防账号枚举

不向未认证调用者暴露"某个邮箱是否已注册"。找回密码发码对未注册邮箱静默返回成功；登录时账号不存在与密码错误返回同一业务码。

## 动机

`service/auth.go` 对同一个风险存在两种相反处理：`SendCode`（注册发码）注释明写"不限账号是否已存在"，直接发信；`SendForgotCode`（找回发码）校验账号，不存在时 `return nil` 静默成功。两者需要统一。

注册发码不校验是必需的——注册必然是给新邮箱发。所以并非所有入口都能统一成"校验"，真正需要统一的是会泄露已注册集合的两个入口：找回密码与登录。

## 决策

1. **找回密码发码**：账号不存在时返回成功但不发信。
2. **登录**：账号不存在与密码错误统一返回 `A0210`，不返回 `A0201`。
3. **注册发码**：不校验账号是否已存在——这是必需的，注册本就是给尚未注册的邮箱发码。
4. 本 ADR 取代 ADR-0001 §2 码表中 `A0201 账户不存在 | 登录/找回密码时` 的适用场景。

## 冲突

与 ADR-0001 §2 码表冲突。该表明确列出 `A0201` 用于"登录/找回密码时"，而代码刻意不这么做。**若不作记录，后来者会照 ADR 把 `A0201` 加回去，重新打开枚举口子**——这正是本 ADR 存在的理由。

## 后果

- 忘记密码的用户输错邮箱时得不到任何反馈，会等一封不会来的邮件。这是换取防枚举的既定代价。
- `A0201` 实际仅用于已认证上下文（如 `GET /api/users/me`）。
- 枚举攻击的威胁模型是"攻击者不控制目标邮箱、靠响应差异判断是否已注册"。只要未注册与已注册两种情况下服务端行为一致（都不发信、都返回成功），攻击者就观察不到差异。
