# 统一防账号枚举

Status: accepted

不向未认证调用者暴露"某个邮箱是否已注册"。找回密码发码对未注册邮箱静默返回成功；登录时账号不存在、密码错误、尝试超限与锁定返回同一业务码与文案；注册的"邮箱已注册"只在验证码校验通过后可见。

## 动机

`service/auth.go` 对同一个风险存在两种相反处理：`SendCode`（注册发码）注释明写"不限账号是否已存在"，直接发信；`SendForgotCode`（找回发码）校验账号，不存在时 `return nil` 静默成功。两者需要统一。

注册发码不校验是必需的——注册必然是给新邮箱发。所以并非所有入口都能统一成"校验"，真正需要统一的是会泄露已注册集合的两个入口：找回密码与登录。

## 决策

1. **找回密码发码**：账号不存在时返回成功但不发信。
2. **登录**：账号不存在、密码错误、失败次数超限与账号锁定统一返回 `A0210` 与同一文案；不返回 `A0201`、`A0241`、`A0242`。锁定/超限只可能发生在已注册账号上，原样返回会让五次错误密码变成存在性探针。
3. **注册发码**：不校验账号是否已存在——这是必需的，注册本就是给尚未注册的邮箱发码。
4. **注册**：先校验验证码，再检查邮箱是否已注册；错码永远回 `A0132`，避免无需验证码的邮箱存在性探针。只有能收到该邮箱验证码的人才会看到 `A0112`。
5. ADR-0001 §2 的码表已按本决策收窄：`A0201` 仅用于已认证上下文，登录/找回密码不得使用。

## 与 ADR-0001 的关系

ADR-0001 §2 的码表曾把 `A0201` 列为「登录/找回密码时」可用，与本节决策相反。**若不作记录，后来者会照那张表把 `A0201` 加回去，重新打开枚举口子**——这正是本 ADR 存在的理由。该表现已改成「仅限已认证上下文」，两文一致；改动码表时必须同时保住这条约束。

## 后果

- 忘记密码的用户输错邮箱时得不到任何反馈，会等一封不会来的邮件。这是换取防枚举的既定代价。
- 被锁定的用户在登录页只会看到"邮箱或密码错误"，不会被告知"账号已锁定"；锁定状态只留在服务端。
- 本 ADR 只统一响应内容，不承诺恒定响应时间。公开登录没有按 IP 限流，给不存在的账号补一次 bcrypt 比对会新增廉价的 CPU 放大；时间侧信道留待引入登录限流后一并处理。
- `A0201` 实际仅用于已认证上下文（如 `GET /api/users/me`）；`A0241` 仍用于发码与验证码校验的限流，不再用于登录响应。
- 枚举攻击的威胁模型是"攻击者不控制目标邮箱、靠响应差异判断是否已注册"。只要未注册与已注册两种情况下服务端行为一致（都不发信、都返回成功），攻击者就观察不到差异。

锚点：`backend/service/auth.go` 的 `Login` 与 `SendForgotCode`；`backend/pkg/errcode` 的 `Map`。
