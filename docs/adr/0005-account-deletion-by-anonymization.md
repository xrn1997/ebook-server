# 账号注销用匿名化而非删除

注销账号时清空凭据与可识别信息、把 `email` 改写为占位值，但**保留数据行与公开评论**；既不硬删除，也不软删除。

## 动机

登录主标识不可变（ADR-0004）之后，必须给一条体面的退出路径：用户换邮箱服务商时，唯一出路是注销再用新邮箱注册。

注销要同时满足三件事：该邮箱能被重新注册、公开评论不悬空、服务端不留原 email。硬删行会让 `Comment.UserID` 悬空；软删则挡不住唯一索引（行还在，索引仍占用），且会让 GORM 的 `Preload("User")` 因自动附加 `WHERE deleted_at IS NULL` 而过滤掉作者——恰好破坏"评论保留"这个目的。

## 决策

1. **注销需邮箱验证码确认**，与改密码的旧密码确认强度对等，使仅持有 access token 的攻击者无法完成。
2. 注销时执行：`email` → `deleted_<uid>@invalid`；`username` 与 `nickname` → `已注销用户_<uid>`；`password` 与 `avatar` 清空；删除该用户全部 `refresh_tokens`。
3. **不设置 `DeletedAt`**。行保持可查询，使评论的 `User` 关联正常返回。
4. **公开评论保留**，作者显示为匿名化后的名字。
5. **操作日志保留**——审计用途，用户不可写、不可删，注销时也不删除。
6. **注销端点在响应中返回用户完整数据**，让用户当场取走；不通过邮件发送附件。

## 被拒方案

**硬删除行** —— `Comment.UserID` 悬空，`Preload("User")` 返回空对象；级联删评论则会破坏其他用户看到的讨论串。

**软删除** —— 不释放唯一索引（同一邮箱无法重新注册），且 `Preload` 会过滤掉已注销用户，评论作者显示不出来。

**`(email, deleted_at)` 部分唯一索引** —— SQLite 与 PostgreSQL 支持，MySQL 不支持，会与 `sql/init.sql` 产生行为分歧；且已注销的行保留原 email 明文，与"服务端不留原 email"冲突。

**注销时邮件发送数据附件** —— 与注销目的方向相反：会在发件方"已发送"、若干中继、收件方邮箱留下至少三份用户控制不了的副本，且 STARTTLS 可被降级、无法端到端保证加密。此外 `pkg/mail` 当前只发 `text/plain`，带附件需改造成 `multipart/mixed`，还受 SMTP 10–25MB 附件限制。

**支持恢复已注销数据** —— 若由服务端自动关联新旧账号，就必须留下某种标识（哪怕是 email 的哈希），与"服务端不留档"互斥；若让用户用导出文件自行恢复，则需引入导入接口，要处理 ID 冲突、重复导入的幂等、内容去重、大小限制与字段白名单，相对"注销后后悔"这一极低概率事件并不划算。

## 后果

- 同一邮箱可无限次"注册 → 注销 → 再注册"，每次产生新的 uid。占位值因 uid 自增唯一而互不冲突。
- 已注销的行永久保留（否则评论关联会断），但不含任何可识别信息与凭据。
- 匿名化后的账号不可登录、不可按邮箱检索——`password` 已清空，`email` 已是占位值。
- 注销后，用户的公开评论永久留在公开列表中，且他再也无法删改；重新注册也拿不回来。这是"保留公开内容"的固有代价。

## 冲突

与 ADR-0001 §3 冲突。该节要求 `refresh_tokens` 通过外键 `REFERENCES users(id)` 级联删除；本 ADR 保留 users 行，级联删除不再发生，注销时需显式删除该用户的 refresh token。
